## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification (SRS) describes the functional and non-functional requirements for the AI Health Care application based on the current implementation.

### 1.2 Scope

The system provides:

- User authentication (login/register) with role-based profiles (patient/doctor)
- Doctor search and availability management (slots)
- Appointment booking and appointment status workflow
- Patient dashboard with medical-related UI (health metrics placeholders) and appointment booking UI
- Video calling using WebRTC (simple-peer) with Socket.IO signaling
- Live chat during calls using Socket.IO events
- Medicine information retrieval via AI (OpenRouter/LLM)
- Ayurvedic chatbot via AI endpoint

### 1.3 Definitions

- **Patient**: End-user who books appointments and joins video calls.
- **Doctor**: End-user who can set availability and receive appointment requests.
- **Admin**: Admin routes exist but logic is not detailed in the inspected files.
- **JWT**: JSON Web Token for API authentication.
- **Room**: Socket.IO room for a video/chat session.
- **SimplePeer**: WebRTC peer library used in the frontend.

## 4. Functional Requirements

### 4.1 Authentication & Authorization

#### 4.1.1 Register

- Endpoint: `POST /api/auth/register`
- Implemented in: `server/controllers/authController.js`
- Requires:
  - `payload` in `req.body.payload` (string JSON or object) as parsed
  - `role` in payload
  - `email`, `password`, and role
  - For patient: `firstName` required
  - For doctor: `firstName`, plus doctor profile fields used in controller
- File uploads (multipart/form-data) are used in the register route via `upload.fields`:
  - `profileImage` (max 1)
  - `medicalLicense` (max 1) (commented in controller logic)
  - `identityProof` (max 1) (commented in controller logic)

#### 4.1.2 Login

- Endpoint: `POST /api/auth/login`
- Implemented in: `server/controllers/authController.js`
- Requires: `email` and `password`
- Uses bcrypt comparison:
  - `bcrypt.compare(password, user.password)`
- Account lock logic exists:
  - `user.isAccountLocked()` and login attempt increment/reset
- Returns JWT + profile data:
  - Patient profile: from `Patient` collection using `userId`
  - Doctor profile: from `Doctor` collection using `userId`

#### 4.1.3 Protected Routes

- Middleware: `server/middleware/authMiddleware.js`
- Reads `Authorization: Bearer <token>`
- Verifies JWT using `process.env.JWT_SECRET`
- Sets `req.user` to the `User` document without password

### 4.2 Doctor Listing & Search

#### 4.2.1 Search doctors

- Endpoint: `GET /api/avail/doctors`
- Implemented in: `server/controllers/doctorController.js` (exported as `getDoctors`)
- Query parameters (based on controller implementation):
  - `search` (matches firstName, lastName, specialization via regex)
  - `specialization` (regex match)
  - `minFee`, `maxFee` (range)
  - `sortBy` (rating/fee_low/fee_high/experience/default createdAt)
- Response:
  - `{ success: true, doctors, count }`
- Controller filters base query by doctor role and verification:
  - `query = { role: "doctor", isVerified: true }`

### 4.3 Availability & Slot Management

#### 4.3.1 Doctor sets availability (Add slots)

- Endpoint: `POST /api/avail/doctors/availability`
- Implemented in: `server/controllers/availabilityController.js` as `Add_slots`
- Auth required for this action via route middleware `auth`
- Request body fields (based on controller):
  - `date` (string)
  - `slots` (array)
- Logic:
  - Normalizes date to midnight UTC
  - Upserts `Available` document:
    - filter: `{ doctorId, date: availabilityDate }`
    - updates: `{ slots, isAvailable: slots.length > 0 }`

#### 4.3.2 Get doctor slots

Two slot retrieval patterns exist in code:

**A) Availability-based slot calculation for a logged-in doctor**

- Endpoint: `GET /api/avail/doctors/:doctorId/slots`
- Route requires `auth`
- Implemented in: `availabilityController.getDoctorSlots`
- Input:
  - `:doctorId` path
  - `date` query parameter
- Output:
  - Reads availability by doctorId and date
  - Reads appointments for that doctor for that day where status in `pending` or `confirmed`
  - Filters availability slots to remove those whose `startTime` are booked

**B) Patient-side slot fetch for a particular doctor**

- Endpoint: `GET /api/avail/doctor/:doctorId/slots`
- Implemented in: `availabilityController.doctorSlotPatient`
- Input:
  - `doctorId` path
  - `date` query parameter
- Output:
  - Returns `slots: availability.slots` if availability exists; otherwise empty array
- Note: From inspected file, this patient-side implementation does not subtract already booked slots.

### 4.4 Appointments

#### 4.4.1 Booking an appointment

- Endpoint: `POST /api/appointments`
- Implemented in: `appointmentController.appointmentBooking`
- Auth required via protect middleware
- Request body (from controller and patientDashboard usage):
  - `doctorId` (doctor profile id per logic)
  - `appointmentDate` (YYYY-MM-DD string; parsed into Date)
  - `timeSlot`:
    - `startTime`
    - `endTime`
  - `type` (defaults to `"video"`)
  - `symptoms` (optional; defaults to empty string)

- Validation:
  - Ensures doctorId, appointmentDate, and timeSlot fields exist
  - Ensures appointmentDate parses to a valid Date
  - Checks if time slot already booked for that doctor on that date excluding `cancelled`

- Response:
  - 201 with `appointment` document

#### 4.4.2 View patient appointments

- Endpoint: `GET /api/appointments/patient`
- Auth required
- Implemented in: `getPatientAppointments`
- Finds patient profile via `Patient.findOne({ userId: req.user._id })`
- Fetches appointments by `patientId` and populates `doctorId`

#### 4.4.3 View doctor appointments

- Endpoint: `GET /api/appointments/doctor`
- Auth required
- Implemented in: `getDoctorAppointment`
- Finds doctor profile via `Doctor.findOne({ userId: doctorId })`
- Fetches appointments by `doctorId` and populates `patientId`

#### 4.4.4 Update appointment status (accept/reject/cancel)

- Endpoint: `PATCH /api/appointments/:id/status`
- Auth required
- Implemented in: `AppointAcceptReject`
- Request body:
  - `status` must be `"confirmed"` or `"cancelled"`
- If status is `confirmed`:
  - generates `appointment.roomId = uuidv4()`
- Appointment state transition validation:
  - only allows update when appointment.status === `"pending"`

- Remote media:

#### 4.5.4 Call controls (frontend)

- Server forwards to room: `socket.to(room).emit('chat-message', { msg, username, timestamp: new Date() })`
- Typing indicator events:
  - `typing { room, username }`
  - Server forwards `typing` to others

#### 4.6.2 Frontend chat component

- Component: `client/src/components/page/VIdeoCalling/chat.vue`
- Props:
  - `socket`, `roomId`, `currentUsername`, `isCallActive`, `showClose`
- Features:
  - Stores `messages[]` locally
  - Emits `chat-message` to backend
  - Shows typing indicator when receiving `typing`
  - Chat disabled visually based on `isCallActive`
